# napari-deeplabcut v0.4.0

A maintenance release, covering compatibility and data integrity.

> [!IMPORTANT]
> Version numbers now follow PEP 440, starting with `0.4.0`.
> Version resolution and the installation of `deeplabcut[gui]` are unchanged.

## Highlights

- A keypoints layer can no longer save its annotations into a folder it does not belong to (#246, closes #245)
  - The keypoints layer is reported and locked for editing instead; saving it works as previously (#246)
- Re-opening the same extracted frames folder no longer loads a duplicate keypoints layer (#246)
- Less use of napari internals, for compatibility with upcoming napari releases (#242)
- The `numpy<2` upper bound is lifted, following DeepLabCut 3.0.2 (#241)

## What you should know

### Files written by earlier versions are not repaired

0.4.0 does not undo writes that already happened. If you labeled several extracted frames folders in one session with 0.3.x, check that each `CollectedData_<ScorerName>` file holds only frames from its own folder.

In the `.csv` next to it, the first column lists one frame per row; every row should name the folder the file sits in.

If any row names another folder, the [napari plugin troubleshooting guide](https://deeplabcut.github.io/DeepLabCut/docs/gui/napari/troubleshooting.html) covers repairing the file.

### New dialogs while labeling, and locked layers

Three situations are now handled differently:

- When a leftover keypoints layer belongs to a different folder than the frames you just opened
- When an annotated frame was renamed or deleted, so it is no longer in the folder
- When the same folder is opened twice; the duplicate keypoints layer is closed for you

In the first two, the keypoints layer is **locked for editing** until it matches the viewer's Image layer again.

**Your annotations are untouched and saving still works**, writing to the layer's own folder.
No file on disk is rewritten.

> [!TIP]
> What each message means, and guidance for resolving it, is in the
> [napari plugin troubleshooting guide](https://deeplabcut.github.io/DeepLabCut/docs/gui/napari/troubleshooting.html).

### napari UI compatibility

Two situations now notify you once per session: napari's point size slider staying visible where the plugin means to hide it, and `Ctrl+V` not pasting keypoints. Both mean the plugin does not recognize your napari version's layer controls. Labeling still works; please report either.

## Bug fixes

- #246 — Fix a keypoints layer adopting an unrelated dataset and saving into it (#245)
- #243 — Fix the config placeholder dialog's choice being forgotten when closing was cancelled, so a later config drop fell back to the default action
- #246 — Reject a folder whose frames match only by filename, which any two dataset folders in a DLC project do
- #246 — Stop keypoints on a deleted frame being re-keyed onto another frame
- #246 — Lock a keypoints layer for editing while it does not match the Image layer in the viewer

## For developers

### NumPy 2 (#241, #247)

The core `numpy<2` bound is removed, following DeepLabCut#3499. DeepLabCut's TensorFlow extras still cap NumPy below 2 on some Python versions, so the NumPy resolved inside a `deeplabcut[gui]` environment depends on which extras are installed, not on this plugin alone.

### napari compatibility canary (#239, #249)

A weekly job now runs the suite against `napari --pre` and against the declared 0.6.6 floor and latest stable, and opens a tracking issue on failure. The release path builds the distribution once and publishes the artifact that was installed and tested.

### Faster test suite (#237)

The suite runs under `pytest-xdist` (`-n auto --dist loadfile`), roughly 290s to 60s locally.

### Layer lifecycle (#243)

Keypoints layers kept bindings to a previous store after reattachment, and a recycled layer id was refused registration because a collected layer had left it behind. Both are fixed.
